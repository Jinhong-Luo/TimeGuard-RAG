# 完整评测与结果复用

本流程固定 RAGFlow v0.27.3、FinanceBench 150 题、84 份原始财报和同一英文 Embedding。当前集合为调优 88 题、开发 39 题、保留测试 23 题。以下是可执行流程与预算估计，不代表已经完成真实端到端评测。

## 冻结条件

正式运行前，84 份文档必须全部完成原生解析，完成六档经 RAGFlow 到 Codex 桥的实际强度传递验证，并保存不含凭据的证明。每档配置只允许模型别名中的强度不同，其余模型实例、检索设置、Embedding、语料、查询文件及上游版本必须一致。实际别名来自服务，不手填未注册标识。

生成和裁判均使用 `--concurrency 2`，六档顺序运行；不要同时进行另一档生成、模型裁判、PDF 重解析或重负载下载。裁判统一为 `gpt-6.1-sol / medium`，其并发也固定为 2。两个命令默认并发为 1，省略参数会形成不同实验条件，不能与并发 2 的记录混用。

各层预算现已统一冻结：桥300秒、RAGFlow330秒、外层请求1200秒、固定medium裁判360秒。RAGFlow额外重试设为0，仍保留1次正常调用；SDK原生2次重试另外记录。六档真实RAG烟测与最终预算单题验证均已通过，证据与原生重试推导见[正式运行预算与驱动](正式运行预算与驱动.md)。不能某档超时后只延长该档再与旧条件混比，也不增加静默重试。小文档连通验证不能保证长财报请求在预算内成功；正式失败仍保留分母。

运行清单保存查询原文件 SHA256、完整题号、语料摘要、源码 SHA256、并发数、模型配置和索引文档快照。`index_snapshot_sha256` 是原生文档列表中 ID、名称、分块数、大小、更新时间的确定性摘要；**它不是全部向量或分块正文的内容哈希**。评测期间禁止修改、重解析或重建知识库，不能仅凭此摘要声称逐块内容已独立校验。文档数量不同、未解析完成或文档快照变化均拒绝运行/复用。

每题重新创建无会话状态的客户端，问答请求不传 `session_id`。生成只读取 `queries.jsonl`，并只发送问题；`gold.jsonl` 仅由离线评分和裁判读取。裁判不看档位标签、候选排名或其他档答案，每次只评当前题已生成答案、标准答案/证据及该答案真正引用的原文。相同模型作为生成器和裁判仍可能存在风格偏好，结果须称模型裁判暂定推荐，后续人工抽查独立报告。

## 六档完整开发集

先准备每档冻结配置 `configs/r0-{effort}.json` 和实际传递证明 `reports/transport-{effort}.json`。下列文件名是流程约定，不会自动生成服务标识或证明。运行前在环境变量设置服务凭证、桥接令牌及 `CODEX_BRIDGE_BASE_URL`，不要把凭据写入命令历史或仓库。

```bash
for effort in low medium high xhigh max ultra; do
  run="runs/dev-complete/$effort"
  python3 -m timeguard.run \
    --config "configs/r0-$effort.json" --split dev --effort "$effort" \
    --transport-proof "reports/transport-$effort.json" \
    --concurrency 2 --output "$run" || exit 1
done

for effort in low medium high xhigh max ultra; do
  run="runs/dev-complete/$effort"
  python3 -m timeguard.judge "$run" --concurrency 2 \
    --base-url "${CODEX_BRIDGE_BASE_URL:?先设置已验证裁判地址}" --execute || exit 1
  python3 -m timeguard.score "$run" --reviews "$run/model_reviews.jsonl" || exit 1
done

python3 -m timeguard.select --review-source model \
  runs/dev-complete/low runs/dev-complete/medium runs/dev-complete/high \
  runs/dev-complete/xhigh runs/dev-complete/max runs/dev-complete/ultra \
  --output reports/effort_selection.json
```

不加 `--execute` 的裁判只显示计划。运行有错误时，错误行与计划分母保留；续跑只补未落盘题，不重复成功或失败题。已有失败需要另立诊断/重跑计划并完整披露，不能修改旧文件直到选出成功答案。最终选择要求六档各 39 个成功答案及 39 个完整布尔答案判断；缺档、缺题、重复题或未知答案判断都拒绝选优。数值口径、引用支持允许 `null`，同时报告覆盖率和未知数。

预先固定质量容差为 2 个百分点。39 题中相差 1 题约为 2.56 个百分点，因此当前样本下通常只有正确题数并列的档位才按平均耗时取更快者；不能据此声称已经测出总体最优档位。`source_runs` 将选择报告绑定每档 `manifest.json`、`results.jsonl`、`model_reviews.manifest.json` 和 `model_reviews.jsonl` 的原始文件 SHA256。生成端只复制这些摘要元数据；裁判复用端核对源裁判确实是选档时的那一版，拒绝选档后替换为另一组自洽判断。

## 选定档位扩展至全量 150 题

选择报告产生后冻结档位，不得看完保留测试再回改开发集或选择规则。全量允许原样复用所选档完整 39 题，只新增调优 88 题与保留测试 23 题，共 111 题。不能复用连通测试、其他档位、其他索引或不同并发结果。

```bash
chosen=$(python3 -c 'import json; print(json.load(open("reports/effort_selection.json"))["chosen_effort"])')
source="runs/dev-complete/$chosen"
target="runs/all-selected/$chosen"

python3 -m timeguard.run \
  --config "configs/r0-$chosen.json" --split all --effort "$chosen" \
  --transport-proof "reports/transport-$chosen.json" --concurrency 2 \
  --reuse-run "$source" --selection reports/effort_selection.json --output "$target"

python3 -m timeguard.judge "$target" --concurrency 2 \
  --base-url "${CODEX_BRIDGE_BASE_URL:?先设置已验证裁判地址}" \
  --reuse-reviews "$source/model_reviews.jsonl" --execute

python3 -m timeguard.score "$target" --reviews "$target/model_reviews.jsonl"
```

生成复用验证选择报告的档位、六档完整评分、选择规则和源文件摘要，再检查同源查询、每题问题、完整 39 题、配置、并发、语料、源码和当前文档快照。它不读取模型裁判原文或金标。复用行保留原答案、引用、用量和逐题耗时，增加 `reuse_origin`，包含源结果文件和原始行字节的摘要。

裁判复用额外核对源裁判清单与开发集生成文件的绑定，验证固定模型、强度、并发、金标、提示、schema 与源码；逐题重新构造裁判输入并比对原输入摘要、原始模型判断和引用映射。通过后保留原判断、用量和耗时，只改新运行签名并保存原签名/文件/行摘要。**不能直接复制裁判 JSONL 后手改签名。**

生成墙钟在 `execution_history.jsonl` 中逐次追加，裁判墙钟在 `model_reviews.execution.jsonl` 中追加。全量清单的 `identity.reuse.source_wall_time_seconds` 保存复用 39 题的原始执行墙钟；新运行历史单列新增结果数和复用数。两份历史都须保留，不能把只运行新增 111 题的墙钟除以 150，也不能把复用 token 当成免费。`mean_seconds` 仍由 150 条原始逐题耗时计算，它是请求延迟平均数，不等于并发吞吐率。重复启动的历史也保留，不能只取最快一次。

## 分组报告与指标边界

公开全量 150 题含参与选择的 39 个开发题，**不能称为独立泛化成绩**。最终报告至少同时列出开发 39、调优 88、保留测试 23、公开全量 150；其中保留测试只做一次冻结后的评价。可在生成与裁判全部结束后用下面的离线评分代码生成分组报告，无额外模型调用：

```bash
python3 - "$target" <<'PY'
import sys
from pathlib import Path
from timeguard.common import read_json, read_jsonl, write_json
from timeguard.score import summarize

root = Path(sys.argv[1])
manifest = read_json(root / "manifest.json")["identity"]
gold = {row["id"]: row for row in read_jsonl("data/financebench/gold.jsonl")}
queries = read_jsonl("data/financebench/queries.jsonl")
rows = read_jsonl(root / "results.jsonl")
reviews = read_jsonl(root / "model_reviews.jsonl")
reports = {}
for split in ("dev", "tune", "test", "all"):
    ids = [row["id"] for row in queries if split == "all" or row["split"] == split]
    report, _, _ = summarize(ids, gold, [row for row in rows if row["id"] in ids],
                            manifest["config"]["retrieval"]["page_size"],
                            [row for row in reviews if row["id"] in ids])
    reports[split] = report
write_json(root / "split_summaries.json", reports)
PY
```

页命中和严格文本匹配是诊断检索代理指标，与问答实际引用分开。RAGFlow 的 `reference.chunks` 含未引用候选；裁判只使用答案显式标记映射到的原文。没有引用但提出事实为不支持，映射或原文缺失为未知，不能把候选列表当成全部已引用。模型评分不等于人工复核，费用未知仍为 `null`。

## 调用数与耗时预算（估计）

无重试、无故障、所有答案均有效时：

| 阶段 | 新生成调用 | 新裁判调用 | 最终结果题数 |
|---|---:|---:|---:|
| 六档开发集 | 6 × 39 = 234 | 234 | 每档39 |
| 所选档扩展全量 | 111 | 111 | 150，含复用39 |
| 合计 | 345 | 345 | 690次模型请求 |

若不复用，合计为 384 次生成与 384 次裁判，即 768 次模型请求。严格复用节省 78 次请求。连通验证、失败诊断、服务注册验证、解析、Embedding 和原生问答内部额外调用不包含在此表；实际次数以桥审计日志为准。每个新生成题还有一次诊断检索和问答内部检索，不能把它们误算成只发生一次召回。独立纯检索 150 题也应另计。

设六档每题平均生成耗时分别为 `g_low … g_ultra`，所选档为 `g_selected`，固定裁判平均耗时为 `j`，理想双并发墙钟约为 `(39 × 六档g之和 + 111 × g_selected + 345 × j) / 2` 秒，另加检索、调度与批次尾部等待。这个估计不保证双倍加速：共享模型限流、网络、上下文长度和服务排队都会改变实际值。

仅作排期情景：若生成平均 45–180 秒、裁判平均 20–60 秒，则 690 次请求在理想双并发下约 **3.1–11.5 小时**，另加解析与上述开销；这不是实测时长。拿到正式日志后应以各档实际延迟和完整墙钟更新预算，不以普通算术烟测耗时外推长财报问答。

实际已冻结的超时与原生SDK重试、六档可运行配置及批次审计驱动见[正式运行预算与驱动](正式运行预算与驱动.md)。文中耗时区间仍是排期估计，正式结果以完整GPU矩阵为准。
