# 复用已解析文档扩充语料

这次扩充保留已由原生DeepDOC成功解析的 `3M_2018_10K` 160页文档，在同一知识库补齐冻结语料中的其余83份。该原文档实际经历了执行器逐步增加的资源阶段；后续83份使用最终8个执行器、每执行器1个任务、16 CPU、48 GiB容器和单张固定GPU。解析算法、模型权重、Embedding、分块256和表格自动旋转true保持一致，不把这次复用描述为全库相同资源下的吞吐实验。

扩充入口是独立模块 `timeguard.extend_corpus`。它不修改现有 `ingest` 或 `run`，不读取问题、答案或金标，也不会上传、删除或重新解析任何原生文档。

先保留并审计归档旧失败的 `data/ingestion.json`；模块拒绝覆盖任何已有输出，不会替操作者删除或移动旧数据。标准入口如下，认证沿用进程环境中的 `RAGFLOW_API_KEY`：

```bash
# 默认只核验本地输入、84份PDF和前后模型/解析器证据，不写输出，不发原生API请求。
python3 -m timeguard.extend_corpus \
  --final-models reports/deepdoc_model_files.final.json \
  --final-parser-evidence reports/gpu_final_parser_evidence.json \
  --task-accounting reports/long_smoke_chunk_accounting.json \
  --evidence reports/gpu_long_smoke_resource_stages.json \
  --evidence reports/gpu_long_smoke_complete.json \
  --evidence reports/gpu_final_runtime_ready.json

# 确认最终服务已就绪且目标输出不存在后，同一命令追加 --execute。
# 原生接口只做GET核验：知识库配置、唯一DONE文档、全部分页分块及核验后的文档快照。
```

默认源文件为 `data/gpu_long_smoke_ingestion.json`、`data/long-smoke/documents.jsonl`，完整语料清单为 `data/financebench/documents.jsonl`，最终资源配置为 `deploy/parse-profile.gpu.json`。模型与解析器的源证据分别为 `reports/deepdoc_model_files.json`、`reports/gpu_long_smoke_parser_evidence.json`。

只有全部核验通过才生成三个新文件：

- `deploy/parse-profile.gpu.corpus.json`：原160页资源条件、资源阶段证据及其原始字节摘要、最终83份资源条件、算法一致性验证与扩充来源。
- `reports/corpus_extension.json`：源state和两个语料清单的原始字节SHA、模型/旋转证据、唯一分块ID及正文/位置摘要、明确的1份复用和83份新增数量。不保存分块正文。
- `data/ingestion.json`：全文84份的语料身份、增强profile，以及原有1份文档的同一ID、PDF摘要和 `parse_requested=true`。原state及小语料清单不变。

报告中的新state摘要指扩充写入时的初始台账；之后原生导入器会正常追加83份记录。通过原生入口继续：

```bash
python3 -m timeguard.ingest \
  --embedding-model 'BAAI/bge-small-en-v1.5@local_tei@HuggingFace' \
  --parse-profile deploy/parse-profile.gpu.corpus.json
```

导入器依据已有文档名和 `parse_requested` 跳过原1份，仅上传并请求解析另外83份。正式运行器会把增强profile完整冻结到运行身份；仍须等待84份全部DONE、纯检索150题和索引快照冻结后才进入模型矩阵。

源profile缺少 `table_auto_rotate` 时，仅在固定v0.27.3源码默认true且源容器有效值已验证的证据下接受；最终profile和容器证据都必须明确true。改变旋转、CUDA模型文件、镜像、解析器源码、OCR环境或知识库解析参数都会被拒绝。资源调度允许变化的字段仅为执行器/任务/分块并发、资源名称、总任务数和已授权的容器内存；每项前后差异均写入来源记录。

## 本次原生计数差异

实际160页的14个成功任务记录476个原始块ID。各任务内部去重后合计462，与原生文档累计计数一致；所有任务ID并集只有455，与完整REST分页返回的455个唯一可用块逐项一致。任务内重复14次，跨任务重复额外计数7次，缺失和多余集合均为空，页段连续覆盖0–160页。

上游按“正文+文档ID”的xxhash64生成块ID，没有把页码纳入ID；每个任务内部先去重，再将数量累加到文档，而Elasticsearch使用相同ID作为索引主键。因此跨页段相同正文会产生累计计数与全局唯一数不同的现象。这是固定底座的原生行为，本项目不修改其计数、块ID或索引逻辑。[块ID及每任务计数源码](https://github.com/infiniflow/ragflow/blob/8090ffd8ba6098813d7f7ec2c4b8774f36c8423a/rag/svr/task_executor.py#L439)、[计数累加](https://github.com/infiniflow/ragflow/blob/8090ffd8ba6098813d7f7ec2c4b8774f36c8423a/api/db/services/document_service.py#L768-L795)、[按ID写入索引](https://github.com/infiniflow/ragflow/blob/8090ffd8ba6098813d7f7ec2c4b8774f36c8423a/rag/utils/es_conn.py#L370-L381)。

`--task-accounting`不是跳过总数检查的开关。模块从原始14条任务的 `chunk_ids` 重建集合并校验成功状态、同文档、连续页段、逐任务计数总和，再重新读取当前原生全部API分块并精确比较集合。任何缺失、多余、缺页或未完成任务都会拒绝。没有该原始证明时，仍要求文档累计数与API唯一数相等。输出分别记录 `native_document_chunk_count=462` 与 `unique_available_chunk_count=455`，不把462称为唯一有效块。

当前每个任务的 `retry_count=1` 表示首次领取：原生字段默认0，领取时即加1，不能据此声称经历过一次失败重试。[字段默认值](https://github.com/infiniflow/ragflow/blob/8090ffd8ba6098813d7f7ec2c4b8774f36c8423a/api/db/db_models.py#L1454)、[领取时更新](https://github.com/infiniflow/ragflow/blob/8090ffd8ba6098813d7f7ec2c4b8774f36c8423a/api/db/services/task_service.py#L230-L240)。

## 原生图片块与真实扩充结果

455个唯一可用块中有454个非空文字块和1个原生纯图片块。该图片块正文为空，只有在 `doc_type_kwd=image`、图片标识属于当前知识库和块ID、原生位置合法且文档/知识库归属正确时才接受；摘要同时包含图片类型、标识和位置。普通空文本仍拒绝，不把图片块当成文本证据，也不删除它来让计数吻合。

原始任务中重复的ID正对应这个空正文图片块。任务ID集合一致只证明既有索引没有缺少任务记录中的唯一ID，不能据此声称PDF里的不同图片内容全部无损保存；本次保持固定上游的原生块ID与索引行为。

上述任务记账与图片分支完成后，真实原生只读核验和扩充写入已通过，部署代理已由原生导入器开始只补83份。知识库沿用原160页文档所在实例；最终完整索引与问答矩阵仍须另行完成，不把扩充成功当作基线质量成绩。
