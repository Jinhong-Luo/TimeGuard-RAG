# 正式运行预算与驱动

底座、检索参数和裁判口径不变。六档真实原生问答已在独立的9页烟测知识库通过，每档都检索到6个候选块并各产生一次非零token模型调用；13.48、9.40、9.60、16.68、18.69、18.17秒仅是连通烟测时长，不能用来选档或代替正式GPU索引成绩。提交版证据为 `reports/rag-native-effort-smoke.json`，答案和完整候选原文保存在忽略目录，公开记录仅含摘要与调用元数据。

## 统一预算

| 条件 | 固定值 |
|---|---|
| 模型桥每轮预算 | 300秒 |
| RAGFlow `LLM_TIMEOUT_SECONDS` | 330秒 |
| RAGFlow `LLM_MAX_RETRIES` | 0，保留一次正常调用 |
| OpenAI SDK | 实际镜像2.41.0，原生默认2次重试，即最多3次尝试 |
| 原生问答外层等待 | 1200秒，六档一致 |
| 独立medium裁判等待 | 360秒，写入裁判配置签名 |
| 生成、裁判并发 | 各2；批次顺序执行，共用桥并发2 |

固定源码中的循环是 `range(self.max_retries + 1)`，所以0表示关闭额外重试，仍正常请求一次。提供商构造SDK时没有传入 `max_retries`，原生配置只能关闭RAGFlow这一层；保留SDK自带的两次重试，不修改上游代码。SDK对连接错误、超时及部分HTTP错误会重试，普通退避上限依次为0.5、1秒；响应的 `Retry-After` 可使每次等待达到60秒。因此采用 `3 × 330 + 2 × 60 = 1110` 秒路径估算，并保留90秒处理余量。超时是分阶段网络预算，1200秒不是任意网络故障下的数学硬总上限。

最终环境已白名单核验为330秒和0次额外重试，随后仅做一次low问答：7.33秒成功，非零检索6块，桥审计恰好1条真实模型调用。详见 `reports/rag-final-budget-smoke.json` 和 `reports/rag-runtime-budget.json`。不允许某档失败后单独改预算继续混比；失败尝试与消耗保留。

源码依据：[RAGFlow提供商构造](https://github.com/infiniflow/ragflow/blob/8090ffd8ba6098813d7f7ec2c4b8774f36c8423a/rag/llm/chat_model.py#L355-L374)、[原生重试循环](https://github.com/infiniflow/ragflow/blob/8090ffd8ba6098813d7f7ec2c4b8774f36c8423a/rag/llm/chat_model.py#L1018-L1030)、[非流式调用](https://github.com/infiniflow/ragflow/blob/8090ffd8ba6098813d7f7ec2c4b8774f36c8423a/api/db/services/llm_service.py#L492-L532)。实际安装SDK与服务源码摘要保存在预算报告。原生非流式链路未发现回答缓存读取；仍逐批核对桥审计，不能仅依据配置声称六档都实际调用了模型。

## 启动条件与入口

启动条件是84份PDF解析及完整索引审计完成、冻结 `data/ingestion.json`，并完成 `runs/r0-gpu-retrieval-all` 的150题纯检索。本次也确认Retail全50题结束后才独占模型桥启动；六档与所选150题现已完成，结果见[正式基线结果](R0正式基线结果.md)。索引保留了同一原生算法下一个CPU页段（12页）的结果，完整硬件来源与恢复阶段写入解析配置；它是GPU辅助的混合硬件索引，历史目录名不构成全GPU证明。六档均使用同一最终冻结索引。每档运行前驱动实时检查全部文档DONE、文档集合及元数据快照与预热记录一致。这里固定的是文档元数据快照，不能称为完整向量内容哈希。正式延迟来自已经做过纯检索预热的索引，不是冷启动延迟。

```bash
# 不发模型请求，只打印计划。
python3 -m timeguard.matrix --stage dev

# 在当前终端静默输入两个本机服务凭据，不写入命令历史或公开报告。
read -r -s -p 'RAGFlow API key：' RAGFLOW_API_KEY
echo
read -r -s -p '本机桥接 token：' CODEX_BRIDGE_TOKEN
echo
export RAGFLOW_API_KEY CODEX_BRIDGE_TOKEN
export CODEX_BRIDGE_BASE_URL='http://172.18.0.1:18864/v1'
python3 -m timeguard.matrix --stage dev --execute

# 六档完整39题与固定medium裁判全部完成、选择报告生成后，再扩展所选档。
python3 -m timeguard.matrix --stage all --execute
```

以上标准入口只依赖仓库代码与进程环境，不依赖忽略目录中的文件。当前服务器也有私有便捷加载器 `.cache/run_module.py`，可代为从权限0600的本机文件加载同样的环境变量；它不是复现必需文件，也不随仓库发布。桥接地址必须指向已验证的本项目网关。

六档配置为 `configs/r0-{effort}.json`，其模型别名由实际注册值冻结。开发集每档先生成39题，再独立裁判39题；仅完整六档才产生明确标记为“模型裁判暂定推荐，未完成人工抽查”的选择报告。全量阶段严格复用已选档39题及其裁判，只新增111题。裁判金标只在生成之后的独立进程中读取，不发送回RAG服务。

六档统一采用失败后停止提交的预算规则：生成和裁判分别最多2题在途；首次传输、生成或裁判非成功状态落盘后，不再补发新题，只收完已经在途的请求。额度错误可能被原生服务包装，故不依赖429或错误关键词猜测。原生SDK已经冻结的重试行为不变，评测端不新增重试。原始失败和已完成结果保留，未发题仍属于清单的完整分母，不记成成功或零成本完成；已有失败记录的同一输出目录不会自动续发。源代码摘要固定该规则，失败不会触发换档、缩题或覆盖重跑。子命令非零退出时，矩阵仍先保存完整本批桥审计窗口、失败调用和部分结果字节摘要，再停止后续批次。

`runs/matrix-execution.jsonl` 保存每个批次的审计字节窗口、实际模型与强度、全部成功及失败尝试、token、源文件摘要和新增结果数。它需要评测期间独占本项目RAG桥；首个成功批次冻结桥源码和指令文件摘要，后续生成、裁判批次必须一致。检测到指纹缺失或漂移、别的档位请求、缺失调用、重复请求ID或成功调用数与新增题数不符时停止后续自动选优，留下记录调查。不会把无调用的缓存返回当成已执行模型，也不会自动覆盖失败。已有结果只有在绑定当前结果原始字节的成功历史审计存在时才允许续跑；中断但没有完整审计的情况须先人工整理证据，不能用空窗口补证。

最终离线报告为 `reports/r0-final-summary.json`，逐组列出开发39、调优88、保留测试23、公开全量150，并分别列出复用39与新增111的生成/裁判墙钟。原始答案、裁判、分组详情与完整审计台账保留在忽略的 `runs/` 目录。具体口径与690次计划调用估计见[完整评测与结果复用](完整评测与结果复用.md)。
